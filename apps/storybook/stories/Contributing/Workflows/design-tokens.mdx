# Design Token Workflow

How to change design tokens and keep Figma and code in sync.

## Overview

The Wylie Dog Design System is **token-based**: visual properties (colors, spacing, typography, and so on) are defined as Figma Variables and synchronized to code through the Token Bridge plugin. The full pipeline reference is `documentation/tokens/token-pipeline.md` in the repository; this page is the contributor's walkthrough.

### Token Flow

```
Figma Variables
      ↓  Token Bridge plugin (push through GitHub: a commit or pull request)
packages/tokens/io/sync/
  ├── primitive.json   — raw OKLCH color scales, spacing values, etc.
  ├── semantic.json    — purpose-driven tokens referencing primitives (Light and Dark)
  └── components.json  — component tokens referencing semantic tokens (Light and Dark)
      ↓  pnpm --filter @wyliedog/tokens build   (process-io, then Style Dictionary)
packages/tokens/io/processed/   — resolved JSON per mode
packages/tokens/dist/
  ├── tokens.css          — all variables
  ├── semantic-light.css  — semantic layer, light mode (:root)
  ├── semantic-dark.css   — semantic layer, dark mode (.dark)
  ├── manifest.json       — full token manifest
  └── index.js / index.d.ts / css-vars.js — JS exports and types
      ↓
React components (via the @wyliedog/ui/styles import)
```

`io/sync/`, `io/processed/` and `dist/` are all committed. A token change appears in all three, and the `rebuild-tokens` workflow regenerates the last two when `io/sync/` changes on a pushed branch.

> **Note:** The build uses [`@tokens-studio/sd-transforms`](https://github.com/Tokens-Studio/sd-transforms) as a Style Dictionary plugin to read DTCG-format token files. It is a utility package, not the Tokens Studio Figma plugin; the Figma side is handled exclusively by the Token Bridge plugin.

## Token Architecture

Tokens are organized in three tiers. Each file is an array with one object per collection, holding its `modes` and a flat `variables` map keyed by the dot-separated token name.

**1. Primitive tokens** — raw values, context-free (`primitive.json`, one `Value` mode)

```json
"color.blue.600": {
  "$type": "color",
  "$value": "oklch(0.546 0.215 262.9)"
}
```

**2. Semantic tokens** — what a color means, with a value per mode (`semantic.json`, modes `Light` and `Dark`)

```json
"color.background.default": {
  "$type": "color",
  "$value": "{color.gray.50}",
  "valuesByMode": { "Light": "{color.gray.50}", "Dark": "{color.gray.950}" },
  "$description": "Main page background color"
}
```

**3. Component tokens** — one per element, part and state of a component, referencing semantic tokens (`components.json`, modes `Light` and `Dark`). Components consume these and nothing else for color.

The names in code are the same names: `color.background.default` is the Figma variable `color/background/default` and the CSS variable `--color-background-default`.

### Token Categories

The system includes tokens for colors, typography (families, sizes, weights, line heights), spacing, borders, shadows, motion, opacity and z-index.

## Making Token Updates

### Scenario 1: Change an Existing Token

**Example: change the primary color**

1. **In Figma:**
   - Open the file that holds the variables and the Token Bridge plugin.
   - In the `semantic` collection, find the primary color variables (the solid fill, its hover tone, the tint and the text that pairs with it).
   - Point them at the new primitive (for example another palette's step 600) in both Light and Dark, or edit the primitive value itself in the `primitive` collection.

2. **Push to code:**
   - In Token Bridge, push the change. It opens a commit or pull request that touches `packages/tokens/io/sync/`.
   - Pull the change into your working copy.

3. **Build and check:**

   ```bash
   pnpm --filter @wyliedog/tokens build
   pnpm check:tokens
   pnpm check:docs
   pnpm check:contrast
   ```

   `check:contrast` resolves every declared foreground and background pair in Light and Dark. It fails when a new color makes a declared pair unreadable, which is the most likely result of changing a brand color.

4. **Verify in Storybook:**

   ```bash
   pnpm dev:storybook
   ```

   Check that components reflect the new color in both modes. If a color does not update, restart the dev server.

5. **Commit the sync, processed and built files together:**
   ```bash
   git add packages/tokens/io packages/tokens/dist
   git commit -m "feat(tokens): change the primary color to purple"
   ```

### Scenario 2: Add a New Token

**Example: add a spacing value**

1. **In Figma:** add a Variable in the right collection and give it the name the code should have (`/` in Figma is `.` in the token name).
2. **Push, pull and build** as in Scenario 1.
3. **Use it.** A component uses a component token for its own spacing; add the component token to `components.json` (through Figma) and reference that.
4. **Document it:** add the token to the relevant Storybook tokens story if it introduces a new step or purpose.

### Scenario 3: Dark Mode Tokens

Dark mode is handled by overriding semantic and component tokens under the `.dark` class. Put the dark value in the token's `valuesByMode.Dark`; the build writes it into `semantic-dark.css`.

The generated output looks like:

```css
/* dist/semantic-light.css */
:root {
  --color-background-default: oklch(0.991 0.003 264.45);
  --color-foreground-default: oklch(0.209 0.01 268.18);
}

/* dist/semantic-dark.css */
.dark {
  --color-background-default: oklch(0.149 0.012 259.72);
  --color-foreground-default: oklch(0.952 0.003 264.48);
}
```

To change dark values, update the Variable mode in Figma, push with Token Bridge, pull and rebuild.

## Token Naming Conventions

The naming rules, and the reasoning behind them, are kept in one place so they cannot drift from this page: `documentation/tokens/naming-convention.md` (how to name and use tokens) and `documentation/tokens/semantic-pairing-model.md` (the semantic color decisions). In short:

- **Three tiers:** primitive, then semantic, then component. A component token references a semantic token; a semantic token references a primitive.
- **Components bind only to component tokens.** A component's color, spacing and state styling come from its own component tokens.
- **States belong to the component layer.** Hover, active, focus and disabled are expressed by a component token that references a semantic tone.
- **Pairs are guaranteed.** A foreground and the background it sits on are declared in `scripts/contrast-pairs.json` and checked by `pnpm check:contrast`.
- **Names match Figma exactly** so export and import stay consistent.
- **Name by purpose, not by value:** `color.background.default`, not `color.gray.50`.

## Build Pipeline Details

### Configuration

The Style Dictionary configuration lives at `packages/tokens/style-dictionary.config.js`. It uses the `@tokens-studio/sd-transforms` transform group to handle the DTCG `$type` and `$value` format, then applies project-specific transforms.

### Building Tokens

```bash
# From the repo root (recommended)
pnpm --filter @wyliedog/tokens build
```

The build runs in sequence:

1. `process-io` — processes the sync JSON files
2. `style-dictionary` — generates CSS variables and the manifest
3. `generate-font-loaders` — creates `@font-face` loader files
4. `generate-token-types` — creates TypeScript literal types

## Validation and Testing

### Token Validation

Before committing token changes, run these from the repo root:

```bash
pnpm --filter @wyliedog/tokens test:tokens   # structure, references, OKLCH ranges
pnpm check:tokens                            # every CSS variable used in code is defined
pnpm check:docs                              # docs and stories reference tokens that exist
pnpm check:contrast                          # declared foreground and background pairs meet WCAG AA
pnpm --filter @wyliedog/tokens run audit     # unused, missing and misnamed tokens
```

Use `run audit`: plain `pnpm audit` is pnpm's own vulnerability audit. `test:tokens` prints many warnings; read the errors, not the warning count.

### Manual Testing Checklist

- [ ] All components render correctly in light mode
- [ ] All components render correctly in dark mode (`.dark` class on `<html>`)
- [ ] No broken token references (check the browser console for missing CSS variables)
- [ ] Typography scales render correctly
- [ ] Spacing follows the defined scale
- [ ] `pnpm check:contrast` passes
- [ ] Animations use consistent timing

## Common Issues and Solutions

### Issue: Token Not Updating in Code

**Problem:** Changed a token in Figma but the component still shows the old value.

**Solution:**

1. Verify the change was pushed from Token Bridge and pulled into `packages/tokens/io/sync/`
2. Run `pnpm --filter @wyliedog/tokens build` to regenerate CSS
3. Hard refresh the browser (Cmd/Ctrl + Shift + R); restart Storybook if it still shows the old value
4. Confirm `@wyliedog/ui/styles` is imported in your app's root layout

### Issue: Broken Token Reference

**Problem:** A token shows `undefined` in rendered output.

**Solution:**

1. Check that the referenced token exists in the JSON source:

   ```json
   // ❌ Typo in reference
   "$value": "{color.blue.60}"

   // ✅ Correct
   "$value": "{color.blue.600}"
   ```

2. Ensure the tier order is correct (component, then semantic, then primitive)
3. Re-run `pnpm --filter @wyliedog/tokens build`
4. Run `pnpm --filter @wyliedog/tokens test:tokens` and `pnpm check:tokens` to surface reference errors

### Issue: Dark Mode Not Working

**Problem:** Dark mode tokens are not applying.

**Solution:**

1. Verify the `.dark` class is applied to `<html>`, not `<body>`
2. Confirm `@wyliedog/ui/styles` is imported; it bundles both light and dark CSS
3. Use browser DevTools to inspect the computed value of `--color-background-default`

### Issue: Build Fails After Token Changes

**Problem:** `pnpm --filter @wyliedog/tokens build` throws an error.

**Solution:**

1. Check the JSON syntax in the modified sync file
2. Run the audit to find structural issues:
   ```bash
   pnpm --filter @wyliedog/tokens run audit:verbose
   ```
3. Ensure every `$value` reference uses an existing token name

## Best Practices

### 1. Always Use Tokens

```tsx
// ❌ Bad — Hardcoded values break theming and dark mode
<div style={{ color: '#3B82F6', padding: '16px' }}>

// ✅ Good — Design tokens via Tailwind v4 CSS variable syntax
<div className="text-(--color-foreground-default) p-(--space-200)">
```

### 2. Respect the Hierarchy

Components consume component tokens. Component tokens reference semantic tokens. Semantic tokens reference primitives. Never skip tiers.

```tsx
// ❌ Bad — Component using a primitive token directly
<div className="bg-(--color-blue-600)">

// ✅ Good — Component using a component token
<div className="bg-(--color-button-primary-background)">
```

### 3. Document Token Decisions

Each token has a `$description`, shown as the Variable description in Figma. Say what the token is for and which foreground or background it pairs with, not which colour it holds:

```
Description: "Main page background color. The default, muted and faint
foreground tokens are readable on it."
```

### 4. Test Across Themes

Always test token changes in:

- Light mode
- Dark mode
- Reduced motion (check animation tokens)
